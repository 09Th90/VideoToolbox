# 校准知识增量同步 —— 管理员手册

- 版本：v1.11.0（条目级增量日志架构，2026-09-13）
- 实现位置：`subtitle_calib_merged.py` 第 8 节「增量同步通道」
- 自动验证：`python subtitle_calib_merged.py selftest-sync`（验收 1-7 + NFR-1/2/5 全断言）

---

## 一、架构总览

v1.10.7 的「多用户对等并集」模型（人人可写、整文件三方合并）在 v1.11.0
收敛为**哑远端 + 条目级增量日志**：

```
普通用户客户端                        哑远端（data/calib_sync_remote/）
  校准入口 ──kb-sync（自动）──►  读取 baseline.json（权威基线，只读）
  learn 收尾 ──kb-push（自动）──►  写入 inbox/<client_id>/<ts>.jsonl（只新建）
  learned-reject ──tombstone──►  同上（否决通知）
  管理员（唯一写基线者） ──kb-compact──►  折叠增量进新 baseline，归档旧文件
```

- 合并只发生在**本地**：生效集 = 基线 ∪ 全部增量（按 `ts+id` 全局序）。
- **幂等**：合并按条目 id 去重，反复重放结果逐字节一致；客户端掉队/基线
  重建（seq 变化）天然对齐，无需水位线。
- **确定性**：同输入必同输出（NFR-1/2），冲突隔离不自动应用（NFR-5）。
- **安全**：增量数据全链路仅 `json.load` + 严格 schema 校验，畸形/非 JSON/
  非法 op 行一律跳过并记日志，**禁止 eval/exec**。

## 二、首次部署（管理员）

1. 把 `subtitle_calib_merged.py` 部署到工作目录（随安装包分发）。
2. 生成首版权威基线（D2「数据通道初始化」，只需一次）：

   ```
   python subtitle_calib_merged.py kb-baseline-init
   ```

   产出 `data\calib_sync_remote\baseline.json`（seq=1，全部内置知识条目，
   author=system，trust=maintainer）。之后所有客户端只需能读到该目录。

3. 验证：`python subtitle_calib_merged.py sync-status` 应显示远端基线
   `seq=1`、维护者 `['system']`。

## 三、客户端日常（无需任何操作）

| 时机 | 行为 |
|------|------|
| 校准入口运行 | 自动 `kb-sync`：拉增量 → 合并 → 三道门 → 应用（幂等；失败静默降级，绝不影响校准） |
| `learn` 收尾 | 自动把本次**新增/变更的 confirmed 候选**导出为增量上传（扩展形态，完整词元） |
| `learned-reject` | 自动以 `tombstone` 增量通知其它客户端（人工否决不可被覆盖） |
| 断网 / 远端不可用 | 增量留档本地 `local_log\`，下次启动补传；同步静默跳过 |

学习库（`subtitle_learned_kb.json`）被远端 confirmed 候选自动注入后，
校准运行时自然生效——无需人工干预。

## 四、管理员运维：kb-compact

增量日志是**只追加**的，时间久了需要压缩（FR-4）：

```
python subtitle_calib_merged.py kb-compact
```

做什么：
1. 重新合并（基线 ∪ 全部增量）；
2. **淘汰**（只从通道移除，不物理删除）：
   - `superseded`：已被取代链覆盖的旧条目；
   - `tombstone`：被人工否决的键；
   - `promoted`：已固化进脚本内置表（BILINGUAL_TERMS / ENTITIES）的条目；
   - `conflict`：冲突隔离区条目（**不折叠进基线**，保留待人工裁决）。
3. 写新 `baseline.json`（seq 递增），并把旧基线 + 全部 inbox 增量
   **只移不删**归档到 `archive\seq_<新seq>\`（可回溯审计）。

压缩后客户端无需任何操作：下次 `kb-sync` 自动以新基线整包对齐。

**建议节奏**：合并积压超过数百条，或每次发布新脚本版本（promoted 条目
变多）后执行一次。

## 五、冲突处理（隔离区）

同 `(table, mode, key)` 出现**不同 value 且无取代关系**时，整组条目进
`data\calib_sync\conflict.json`（永不自动应用），`sync-status` 可见：

```
冲突隔离  : N 组（conflict.json，永不自动应用）
```

处置（管理员）：
1. 阅读冲突条目（author / ts / value / evidence）；
2. 裁决后由权威用户以 `supersedes` 增量覆盖，或直接改内置表后
   `kb-compact`（promoted 淘汰）——冲突组不折叠，自然退出通道。

## 六、信任分级（NFR-5）

- `maintainers` 名单（baseline meta 与本地 `data\calib_sync\config.json`
  的 `maintainers`）或条目 `trust=maintainer` → 标注 `maintainer`；
- 其余普通用户条目 → 标注 `observed`（照常生效，仅日志区分来源）。
- 两条都**应用**，分级用于审计与后续策略，不影响合并。

## 七、回滚与禁用

| 手段 | 效果 |
|------|------|
| `VT_SYNC_MODE=legacy` | 整体退回 v1.10.7 行为：不拉取、不合并、不应用增量（校准入口静默跳过） |
| `VT_NO_SYNC=1` | 强制关闭同步 |
| `config.json` 的 `disabled_keys` | 条目级禁用：`[["LEARNED_CANDIDATE","bi","荷鲁斯说你好"], ...]`，被禁键不应用 |

环境变量仅在进程内生效（适合临时降级）；`disabled_keys` 持久生效（适合
定点封禁坏条目）。

## 八、目录与日志

```
data\calib_sync_remote\           哑远端（可 VT_SYNC_ROOT 覆盖）
  ├─ baseline.json                权威基线（seq / meta / entries）
  ├─ inbox\<client_id>\*.jsonl    各客户端增量（只新建，绝不改写他人文件）
  └─ archive\seq_<N>\             kb-compact 归档（旧基线 + 旧增量，可回溯）
data\calib_sync\                  本机同步状态（可 VT_SYNC_DIR 覆盖）
  ├─ config.json                  client_id / 水位线 / maintainers / disabled_keys
  ├─ applied.json                 生效集（校准运行时兜底注入）
  ├─ conflict.json                冲突隔离区
  ├─ calib_sync.log               全量同步日志（合并/冲突/拒绝原因）
  └─ local_log\<client_id>\       未上传留档（断网补传）
```

排查从 `calib_sync.log` 看起：每条记录含 条目 id、拒绝原因、冲突隔离明细。

## 九、关键命令速查

| 命令 | 角色 | 用途 |
|------|------|------|
| `kb-baseline-init` | 管理员 | 由内置知识生成首版基线（仅一次） |
| `kb-sync` | 全部 | 拉取 + 合并 + 三道门 + 应用（校准入口自动执行） |
| `kb-push --learned 库` / `--file 增量.jsonl` | 全部 | 手动导出/上传增量 |
| `kb-compact` | 管理员 | 折叠增量进新基线 + 淘汰失效条目 + 归档 |
| `sync-status` | 全部 | 本机状态：client_id / 水位线 / 生效 / 冲突 / 日志 / 远端基线 |
| `selftest-sync` | 全部 | 验收 1-7 + NFR-1/2/5 自动化断言（隔离临时环境，不碰真实数据） |
