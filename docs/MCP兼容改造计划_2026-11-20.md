## 0. 结论先行

**可行，且改造成本远低于预期。**



| 判断项              | 结论                                                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- |
| 是否适合做 MCP Server | **是**。`agent_cli` 已是 "无 Qt、单 JSON 信封、退出码语义稳定" 的 11 子命令统一入口，天然就是一层 tool 面                                            |
| 首选架构             | **外层 stdio MCP Server + 内层&#x20;**`api_worker`**（API 层）子进程中继**：CLI / MCP 并列，共用 `features\_api\`                     |
| **交付对象**         | **工具箱自身**：`agent_cli`（CLI，已有）、`src\mcp_server.py`（MCP，新增）并列为一等入口，二者只依赖 `features\_api\`；**不依赖、不修改内置 harness**（§3.5） |
| **三层文件独立性**      | **现状不满足**：无命令级 API；CLI 文件自带业务编排；`pipeline.py:440` 反向调 CLI。改造后 CLI / MCP 入口零耦合、共用 `_api`（§3.0）                       |
| 不建议的做法           | 把 MCP 直接塞进 GUI 主进程 / 复用 GUI exe 做 stdio server（两处硬伤，见 §2.3）                                                         |
| 依赖成本             | `mcp==2.3.0` 干跑需新增 12 个包（约十余 MB），pydantic /anyio/httpx2 等主干依赖**已全部在位**                                              |
| 工作量预估            | 约 **7.5 人日**（P0–P4 + P0.5 入口抽离，含验收与文档）                                                                              |
| 最大风险             | 长任务（下载 / 转录 / 硬烧录）与 MCP 同步调用模型的冲突 → 用**异步任务句柄**兜住（§6）                                                               |
| **CLI 参数覆盖**     | 8 个可反射命令 **33/33**；3 个透传命令 **10/19**（本版已按 §4.3 重建）；整体 ≈ **83%**                                                     |

## 1. 兼容目标：先分清两个方向

"兼容 MCP 格式" 在本项目里可以指两件事，二者互不冲突，但优先级与工作量不同：



| 方向                | 含义                                                                                                       | 本次定位                                    |
| ----------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| **A. 对外（Server）** | 工具箱作为 MCP Server，被 Claude Desktop / Claude Code / Cursor / Codex / Trae 等外部 host 挂载，模型直接把「翻译字幕」「切片」当工具调用 | **本期主目标**                               |
| **B. 对内（Client）** | 由某个 AI 托管（如内置 `harness`）作为 MCP 客户端去挂载 Server                                                             | **本期不做**：`harness` 是只读第三方部署，不是本工具箱的交付通道 |

> **本方案只对工具箱自身负责**
>
> ：CLI（已有能力）与 MCP（新增能力）是同一套 
>
> **API 层**
>
> 的两个
>
> **原生入口**
>
> ，任一方都不依赖 
>
> `harness`
>
> 。外部 host 只要能启动 
>
> `tools\python\python.exe`
>
> ，就能接入；工具箱有没有装 harness、harness 是否启用，都不影响。
> 因此 
>
> `agent_cli`
>
>  不是 "过渡形态"，MCP 也不是它的 "协议投影"：
>
> **业务能力收敛在&#x20;**
>
> `features\_api\`
>
> ，CLI 与 MCP 在文件上互不 import。新增功能 = 一个 
>
> `_api\commands\<id>.py`
>
>  \+ 一个 
>
> `cli.py`
>
>  参数壳 + 
>
> `tool_specs.py`
>
>  注册一行；MCP 层不复制业务逻辑，也不调用 
>
> `agent_cli`
>
> 。

### 2.3 三个必须尊重的工程事实（决定架构）



1. **引擎代码有 424 处裸&#x20;**`print()`（27 个文件；重灾区 `calib_core\inspect.py`、`core\download\media.py`、`calib_entity\cli.py` 等）。

   → 若把 MCP Server 与引擎**同进程**跑，任何一行 `print()` 都会写进 stdout，**直接破坏 JSON-RPC 帧**。

2. **CWD 是隐式契约**：`calib_core.learn` 的 `LEARNED_KB_DEFAULT = "subtitle_learned_kb.json"` 是**相对路径**，校准会把学习库写进当前工作目录；`calibrate` 回退通路显式 `cwd=APP_ROOT`。

   → Server 必须 `cwd = 程序根`，且**每次调用都应独立**（`--data-root` 会写 `VT_DATA_ROOT`，同进程复用会串味）。

3. **GUI 主 exe 不能当 stdio server**：`packaging\视频工具箱.spec` 两个分支都是 `console=False`（窗口态），Windows 窗口态进程不保证 `stdin/stdout` 可用；且主 exe 是 PyInstaller 冻结体，外部 host 无法 " 用 Python 调 `src\agent_cli.py`"。

### 2.4 分发现状（决定安装版怎么接）



| 探测项            | 结果                                                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `视频工具箱.iss` 已铺 | `..\src\agent_cli.py` → `{app}\src`；`..\src\features\*` → `{app}\src\features`；`..\tools\python\*` → `{app}\tools\python`（**27 673 个文件 / 约 2 408 MB**） |
| 结论             | **安装版用户机器上，源码 + 内置 Python 都是齐的**，只需再补一个 `src\mcp_server.py` 与 `mcp` 包，**不必新增第二个 exe**                                                                  |
| 若坚持 exe 形态     | 必须单独构建 `console=True` 的 `视频工具箱MCP.exe`（与 GUI exe 分开），否则 stdio 不可用                                                                                      |

### 2.5 外部参照：host 侧行为（非依赖）

以下几点来自 MCP 生态的实测文档，**只作为参数参照，不构成依赖**；工具箱的 Server 由自身启动与分发。



* 协议：官方 SDK 优先协商 **2026-07-28**，回退旧版；服务端不自造版本号。

* 超时：标准 host 的 `tools/call` 默认约 **60 000 ms** —— 这是 §6 必须做异步任务句柄的直接原因。

* 命名：部分 host 会给工具加 `mcp__<serverName>__` 前缀；服务端只保证原始名稳定，前缀由 host 决定。

* 环境：部分 host 会剥离 `*KEY/PASSWORD/SECRET/TOKEN*` 与 `DSH_*` 变量；本方案所需 env（`VT_DATA_ROOT` / `VT_MCP_*` / `PYTHONUTF8`）不含敏感词，可安全穿过。

## 3. 架构方案（含选型对比）

### 3.0 入口独立性审计（API / CLI / MCP）

> 结论：
>
> **现状不满足 "三层文件彼此独立"**
>
> 。项目里没有命令级 API 层，CLI 文件承担了业务编排；更有一处引擎反向调用 CLI。按初稿直接加 MCP，会再叠加两处 MCP→CLI 依赖。
> **"彼此独立" 的操作定义**
>
> ：入口文件互不 import、互不拼接对方路径、无环形依赖；共享业务下沉到中立的 
>
> `_api`
>
> 。
> 采用 
>
> **I1**
>
> ：CLI / MCP 两个入口零耦合，各自只依赖 
>
> `_api`
>
> ；
>
> `_api`
>
>  不反向依赖任何入口。
> 不采用 
>
> **I2**
>
> （CLI 也 fork 
>
> `api_worker`
>
> 、三边完全零 import）：每次调用多一个 Python 进程，
>
> `--data-root`
>
>  / 退出码语义要重做，收益仅是形式上的绝对隔离。

#### 现状实测



| 检查项                             | 实测证据                                                                                                                                                          | 判定              |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| 命令级 API 是否存在                    | `src` 全树无 `*api*.py`；`video_toolbox.py` 是引擎门面（`from core.* import *`），不是命令 API                                                                                | ❌ 缺失            |
| `FeatureSpec.services` 是否承担 API | 17 个功能包中 9 个声明 services，全仓 `registry().service(...)` 仅 **3 处**，且全是 `build_page` 页面挂载                                                                          | ❌ 不是业务 API      |
| CLI 是否只做参数 / 输出                 | `features\<id>\cli.py` 直接编排：`download`（job 分流）、`split`（probe/plan/split）、`translate`（线程池）、`transcribe`（TaskFactory）、`compose`（ffmpeg 命令）、`automation`（UIA 透传） | ⚠️ 业务逻辑在 CLI 文件 |

>
> **不是**

`features\_api\` 用下划线前缀：注册表 `discover()` 只收非下划线包，因此它**不会**被当成功能、也不需要 `FEATURE` 清单；命名与现有 `_cli.py` / `_registry.py` 的 "共享接缝" 一致。

#### 四条硬规则



1. `features\mcp\**` 与 `mcp_server.py` **不得**出现 `agent_cli` / `features.*.cli` 的 import，也不得出现 `agent_cli.py` 路径字符串。

2. `features\<id>\cli.py` 与 `agent_cli.py` **不得** import `mcp` / `mcp_server` / `features.mcp`。

3. `features\_api\**` 与 `api_worker.py` **不得** import CLI / MCP 入口层，也不得 import Qt；可以 import L0 引擎。

4. 参数只有一份真源：`features\_api\spec.py`。MCP 的 `inputSchema` 从它生成；CLI 过渡期保留现有 argparse，由 parity 测试强制等价（后续可选改为生成式）。

#### 门禁（防回退）



* `scripts\check_entry_isolation.py`：AST 扫 import + 字符串扫路径，命中规则 1–3 即非零退出。

* `scripts\check_schema_parity.py`：`_api\spec.py` ↔ `agent_cli --help` ↔ `tools/list` 三方逐项 diff。

* 两者挂到打包前检查（或 CI），不过不出包。

#### 迁移顺序（机械搬迁，不改行为）



1. 建 `_api\spec.py`：11 个命令的参数定义从 `cli.py` /calib 表抽成纯数据；

2. 建 `_api\commands\<cmd>.py`：把现有 `cmd_*` 的**编排段**原样搬入，返回信封 dict；`cli.py` 只留 `setup_*` 与 `_emit`；

3. 建 `api_worker.py`：stdin 读 `{cmd, params}`，调 `_api`，把信封写 `--out` 文件；进程内 `sys.stdout` 全部重定向到 stderr（杜绝 424 处 `print` 污染）；

4. MCP 执行通道接 `api_worker.py`，schema 读 `_api\spec.py`（P1 起生效；P0 骨架只做协议与 echo 工具，不碰业务）；

5. `pipeline.py` 的 `transcribe` 改走 `_api`，去掉对 CLI 的反向依赖；

6. 跑 11 条 golden JSON 对比（改造前 vs 改造后），差异必须为 0。

### 3.1 三种可选形态



| 方案                                | 做法                                                                                                               | 优点                                                         | 硬伤                                                             | 结论                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------ |
| **A 同进程中继**                       | Server 进程内 `import agent_cli` → 直接调 `args.fn(args)`                                                              | 无进程开销，\~1.2 s 一次                                           | 424 处裸 `print()` 污染 stdout（不可控）；引擎 / 任务状态跨调用串味；单次崩溃拖死整个 Server | **否**（仅可用于 `status`/`info` 这类只读且输出收敛的命令，作为后续优化项） |
| **B 子进程 API 中继（首选）**              | Server 收到 `tools/call` → `tools\python\python.exe src\api_worker.py --out <tmp>`（stdin 传 `{cmd, params}`）→ 读结果文件 | **stdout 完全隔离**；MCP 与 CLI **零文件耦合**（都只调 API）；崩溃 / 取消都在子进程内 | 需先做 P0.5 API 抽离（约 2.5 d）                                       | **✅ 采用**                                         |
| **C 静态包装（纯手写 11 个 tool → 直接调引擎）** | 绕过 API 层                                                                                                         | 延迟最低                                                       | 要重写 11 套参数 / 产物 / 错误逻辑，与 `SKILL.md`/CLI 三处漂移；违背 §3.0 "业务只写一遍"  | **否**                                            |

> **交付对象是工具箱自身**
>
> ，不是任何内置托管。

1. **CLI 不因 MCP 而降级**：`agent_cli` 的命令名、旗标、退出码、`--json` 契约全部冻结；MCP 不是 CLI 的包装，而是同一 API 的第二入口。

3. **两边不各写一套**：新增功能 = `_api\commands\<id>.py`（业务）+ `cli.py`（参数壳）+ `tool_specs.py` 注册一行；MCP 不复制业务逻辑。

## 5. 结果与错误映射



| CLI 侧                  | MCP 侧                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------- |
| stdout JSON 对象         | ① `structuredContent`（原样，保 `ok` 字段）；② `content[0] = text`（人读摘要，键值行，≤ 2 KB）         |
| `ok: true` + 产物路径      | 追加 `content[i] = resource_link`（`file://` URI + `name`，指向 `agent_out` 下的 SRT / 视频） |
| `ok: false` + `error`  | `isError: true`，`text` = `error` 原文（**不吞**，CLI 的错误文案就是排障入口）                        |
| 退出码 1 且 `error` 为空     | 仍按失败处理，附 `exit_code`                                                               |
| `audit`**&#x20;退出码 1** | **不置&#x20;**`isError`；返回 `ok:false` 数据 + 文本 "发现 N 处候选，见报告"，因为这是 "检查结果" 而非 "工具故障"   |
| stderr 过程日志            | ① 默认静默（不刷客户端 UI）；② 当客户端带 `progressToken` 时，按行节流转 `notifications/progress`（P3 可选）   |
| 副产物（报告 / 切片目录）         | 全部走 `resource_link`，不内联大文本                                                         |
| 超大 JSON（未来若出现）         | 截断到 8 KB + 落 `agent_out\…json` 并给链接                                                |

## 6. 执行模型：快 / 慢双轨（本方案的核心设计）

MCP 的 `tools/call` 是**请求 - 响应**语义，而本项目最常用的下载 / 转录 / 硬烧录动辄几分钟。标准 host 的默认超时普遍在 **60 s 量级**（实测参照值 60 000 ms）。因此必须双轨：

### 6.1 快轨（同步返回）

`vt_status` `vt_info` `vt_audit` `vt_stabilize` `vt_translate` `vt_calibrate` `vt_compose(soft)` —— 直接 `await subprocess`（上限 300 s），返回完整结果。

### 6.2 慢轨（异步任务句柄）

`vt_transcribe` `vt_download` `vt_split` `vt_compose(burn|mkv)` `vt_bili_submit`：



```
tools/call vt_download {url, height}
   → 立即返回 {task_id: "vt-20261120-153012-a1b2", state: "running", out_dir: "…"}
   → 后台持有一个子进程；stderr 末行缓存为 progress 摘要
tools/call vt_task_status {task_id}   → {state, progress, elapsed_s, last_log}
tools/call vt_task_result {task_id}   → 完成后一次性给出结构化结果 + resource_link
tools/call vt_task_cancel {task_id}   → 杀进程树（ffmpeg/yt-dlp 子进程一并）
```



* 任务表：进程内 `dict` + `data\agent_out\.mcp_tasks\<task_id>.json`（**Server 重启后可恢复查询**，因为产物与状态都落盘）。

* 保留期：7 天；超期仅清状态文件，不动产物。

* **不做**"长任务阻塞式同步"—— 那是最容易被 host 判超时、且难取消的形态。

### 6.3 并发与串行化



| 约束                                           | 策略                                            | 依据                                                                      |
| -------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------- |
| 重资源任务（ffmpeg/ASR/ 下载）                        | 全局 `asyncio.Semaphore(2)`，超出排队并回报 `queued` 状态 | 避免 4 路 ffmpeg 把机器打满                                                     |
| `vt_calibrate` / `vt_stabilize` / `vt_audit` | **串行锁（1）**                                    | 三者都会读写根目录 `subtitle_learned_kb.json`（相对 CWD），并发会互相覆盖                    |
| 同秒产物目录                                       | **必须显式传&#x20;**`--out`**（带 task\_id）**        | `_agent_out_dir()` 只到秒级（`%Y%m%d-%H%M%S`），两路并发会落同一目录并互相覆盖 —— **实测确认的隐患** |
| 单次调用                                         | 不共享 `args` 对象、不共享环境变量                         | `--data-root` 会写 `VT_DATA_ROOT`，必须每子进程独立                                |

### 6.4 Windows 专项



| 项         | 处理                                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------------- |
| 管道编码      | 子进程 `env` 强制 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`；读回时 `encoding="utf-8"`，兼容 `\r\n`                     |
| 中文 / 空格路径 | 全程 `list[str]` argv，`shell=False`；配置里用 JSON 数组而非命令行                                                       |
| 控制台闪窗     | `subprocess` 加 `creationflags=CREATE_NO_WINDOW`（stdout 已是管道，不影响）                                          |
| 取消        | `CREATE_NEW_PROCESS_GROUP` + 进程树终止（`taskkill /T /F <pid>` 或 `psutil` 不可用时自实现遍历 WMIC）                      |
| stdio 帧   | Server 自身走 SDK 的 stdio 传输（SDK 负责跨平台换行）；**不要自实现 JSON-RPC 读写**，也不要自己 `print` 到 stdout（Server 内所有日志走 stderr） |

3. **本期不改 GUI 页面编排**：`page.py` 不 import CLI，不影响 "CLI / MCP 文件独立" 的结论；GUI 后续可选接入 `_api`（与 `split\page.py` 双份编排一并收敛），不在本次验收范围。

4. **不把 MCP 塞进 GUI 主进程**：与 §2.3 三条事实冲突。

5. **不把&#x20;**`harness`**&#x20;纳入链路**：它是只读第三方部署；既不作为 MCP 客户端依赖，也不修改其配置，不参与本期交付。

6. **不追求 "全功能平权"**：`voiceprint` 独立脚本（enroll/score/filter/sync）与 GUI 专属能力（字幕编辑器、工作台）本期不暴露；后续可作为 `vt_voiceprint_*` 第二批工具（需先确认无 Qt 依赖链）。
