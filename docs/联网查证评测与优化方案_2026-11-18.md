# 字幕校准 Agent「联网查证」能力评测与优化方案

> 评测对象：`src/features/calibrate/calib_web_agent.py`（联网工具）+ `src/features/calibrate/calib_ai_agent.py`（Agent 主循环）+ `src/core/calibrate/ai.py`（注入点）
> 明确边界：**不是 DSH / DeepSeek Harness**，是本项目内置的 AI 校准 Agent（v1.16.x 单智能体链路）
> 评测时间：2026-11-18｜方法：本机真实出网实测（非纸面推断）
> 结论一句话：**引擎是好的，链路是坏的；搜索放错了层级，证据没有分级。**

---

## 一、结论先行

1. **引擎可用，链路不可用。** cn.bing 直连 0.28–0.35s、稳定返回 5 条结果；但 `web_fetch` 对任何含中文路径的 URL **100% 抛 `UnicodeEncodeError`**，而灰机 wiki（403）、百度百科（403）、萌娘（403）、Fandom（12s 超时）全部抓不动 —— 深挖这条腿实际是残废的。
2. **搜索发生在错误的层级。** 联网工具只挂在块级 `_ask_block`；最该联网的「官方中文核对」在第 9 步 `build_meta`，**完全离线、且跑在所有校准块之后**。官方名无法参与改写，只能事后用 `_adopt_official_terms` 打补丁（且只接受「把握=高 + 中文目标 + 2~8 字 + 片中已出现」）。
3. **模型不知道该搜什么。** 块级提示词的术语规则是 `select_rules_for_chunk` 按「本块命中才给」，空块直接显示「（空）」；同时提示词里没有片源作品上下文（只有 `mode_flag`），query 全靠模型自由发挥。
4. **结果处理没有「证据」概念。** 有 `b_algo` 就算命中，噪声照样回填（实测「战双帕弥什 远信回响」前 5 条全是「战」字百科）；来源不分级（官网 / BWIKI / 百度百科 / 贴吧平权）；英文查询返回的 `bing.com/ck/a?...` 跳转链未还原。
5. **成本结构危险。** `calib_think_rounds=0` 的界面文案是「关闭（不限）」，代码语义却是「不限、内部 32 轮硬顶」；每次工具轮 = **一次完整块级 LLM 调用**（400 cue 块约 2–4 万 tokens 上下文），单块最坏 32 次。

| 目标 | 结果 |

## 四、问题清单（按优先级）

### P0 — 正确性缺陷（不修则联网等于白开）

| ID | 现象 | 证据 | 根因 / 位置 | 改法 |
|---|---|---|---|---|
| P0-1 | 中文 URL 抓取必崩 | 100% 复现 `UnicodeEncodeError` | `calib_web_agent.py:69-87 _http_get` 直接把含非 ASCII 的 URL 交给 `urllib.request`，http.client 用 ascii 编码请求行 | 请求前对 path/query 做 `quote(unquote(...), safe="/:@!$&'()*+,;=%")`，保留已有百分号编码 |
| P0-2 | 英文/混合查询拿到跳转链 | `ensearch=1` 时 5/5 链接为 `bing.com/ck/a?...` | `_parse_bing` 不还原 | 正则抽 `u=a1aHR0c...` 的 base64 目标，或 fetch 时取 `r.geturl()` 回写 |
| P0-3 | 噪声结果照样当证据回填 | 「崔林特尔梅之金」回填「崔姓_百度百科」 | `_parse_bing` 有 `b_algo` 即算命中，无相关性判定 | 结果过滤：query 分词后要求「术语词」出现在标题或摘要；全不命中则视为无结果 |
| P0-4 | 来源不分级 | 官网首页、BWIKI、百度百科、贴吧同权 | `_format_results` 只列标题/链接/摘要 | 每条打来源标签（`官网 / 维基 / 百科 / UGC`）并按 官网 > BWIKI/灰机/Fandom > 百科 > UGC 排序；UGC 标注「仅作旁证」 |
| P0-5 | fetch 抓到导航壳 | BWIKI 正文 32,962 字符，前 3,500 全是导航 | `MAX_FETCH_CHARS=3500` + 从头截断 | ① 上限提到 6,000；② 按 query 关键词取窗口（命中位置 ±2,000 字符）；③ 对 `*.biligame.com` 自动改写为 `index.php?title=...&action=raw` 抓 wikitext |
| P0-6 | DDG 白等 12s | 国内 100% 超时 | `calib_web_agent.py:186-198` 串行顺位 | 超时降到 5s，且只在前两个 Bing 都抛异常时才尝试；或直接删掉（国内无收益） |
| P0-7 | 工具请求被截断但不告知 | 模型发 3 个只执行 2 个 | `calib_ai_agent.py:829 reqs[:2]` | 回填文本加一行「你请求了 N 个，本轮只执行前 2 个」 |
| P0-8 | 证据无总量上限 | 32 轮累积 `evidence` 全拼进 prompt | `calib_ai_agent.py:934-935 / 2233-2236` | 证据保留最近 8,000 字符（按轮淘汰最旧），超出时在块尾注明「已截断」 |

### P1 — 架构缺陷（决定优化上限）

| ID | 现象 | 根因 / 位置 | 改法 |
|---|---|---|---|
| P1-1 | 最该联网的「官方名核对」离线 | `build_meta` 无 `web` 参数（`calib_ai_agent.py:2818-2820`），且在全部块校准之后（`:2045-2062`） | 把「术语盘点 + 联网核实」前移到第 3 步（载入 KB 之后、切块之前），产出 `extra_rules` 注入 `rules`，再进 `select_rules_for_chunk` |
| P1-2 | 模型没有候选清单 | `select_rules_for_chunk` 只给本块命中（`:584-610`） | 代码侧产出候选：知识库 hot 命中 + 采样里的「2~8 字高频专名 / 拉丁串」，一次轻量 LLM 调用提候选（只输出 JSON 列表，不核实） |
| P1-3 | 权威源没被复用 | `calib_entity/wiki` 已有 `WikiClient.search/page_wikitext`，但 `page_wikitext` 返回 dict（`client.py:86-89`） | 修返回类型（`wikitext["*"] if isinstance(..., dict)`），并加 `page_content()` 走 `prop=revisions&rvslots=main`；联网 Agent 新增 `wiki_lookup(term, work)` |
| P1-4 | query 不受控 | 提示词只说「查术语/专名」，无模板 | query 规范化：去噪词（官方名称/官方中文/叫什么/是什么/怎么读）+ 强制 `作品名 + 术语`；作品名从 `mode_key` 映射或 `orig_title` 推断；0 命中时退化为裸术语 |
| P1-5 | 缓存粒度粗 | `make_tools` 的 cache key = query 原文 | 归一化后缓存（去噪、去空格、小写），跨块/跨轮共享；另加 `term→evidence` 二级缓存 |
| P1-6 | 搜索成本不可见 | 报告只有「N 次工具调用」 | 统计并写报告：搜索次数 / 命中数 / 触发术语 / 采纳自证据的改动数 / 联网耗时占比 |

### P2 — 体验与策略

| ID | 现象 | 改法 |
|---|---|---|
| P2-1 | `think_rounds=0` 文案「关闭（不限）」误导 | 界面改「不限（安全上限 32 轮）」；默认值建议 1 |
| P2-2 | 块级搜索与块级 LLM 强耦合，一轮 = 一次全量重发 | 阶段 2 落地后，块级只保留 `web_fetch`（打开已发现链接），搜索全部收敛到片源级 |
| P2-3 | 无「证据强度」标注 | 回填块头部加 `【证据强度】官网原文 / 维基 infobox / 百科摘要 / UGC 旁证`，模型据此决定是否采纳 |
| P2-4 | 单一来源即下结论 | 同一术语至少 2 源一致才升为 high；冲突时写入 `reason` 而不是静默取舍 |

## 五、推荐优化路线

### 阶段 0：修正确性（0.5 天，零行为变化）

只动 `calib_web_agent.py` 三个函数：`_http_get`（URL 编码）、`_parse_bing`（ck/a 还原 + 相关性过滤 + 来源分级）、`fetch`（关键词窗口 + raw 兜底），加 DDG 超时收敛与请求截断告知。

验收：11 术语集噪声回填 ≤ 1/11；中文 URL fetch 成功率 100%；单次查询平均 < 1s。

### 阶段 1：把「核实」变成独立阶段（1–2 天）

新增 `src/features/calibrate/calib_term_resolver.py`（**feature 包内，不新增顶层模块**）：

```python
extract_candidates(chat, sample_text, mode_key, orig_title, max_n=24) -> list[str]
resolve(web, sites, candidates, work, log) -> {
    "resolved": {term: {"official", "confidence", "source", "snippet"}},
    "unresolved": [...], "stats": {"searches": n, "wiki": n, "hits": n, "seconds": t},
}
as_rules(resolved) -> list[tuple[str, str]]      # 注入 rules
format_block(resolved) -> str                    # 注入 meta prompt 的「已核实术语」
```

流程改造（`calib_ai_agent.calibrate`）：

```
载入 KB → [新增] 术语盘点 + 联网核实 → 合并 rules → 切块 → 逐块校准（块级搜索默认关）
                                   ↘ 结果写报告「联网确认」章节 + 供 _adopt_official_terms 复用
```

证据判定优先级（写死，不让模型自由心证）：

1. 官网页面原文含该术语 → high
2. BWIKI / wiki.gg infobox `|名称=` / `|中文名=` → high
3. Bing 摘要明确「X，游戏《Y》中的角色/地名」→ medium
4. 只有 UGC（贴吧/知乎/TapTap）→ low，**不进 rules，只作报告备注**

成本账：24 个候选 ×（1 次 Bing 0.3s + 条件 1 次 Wiki 0.8s）≈ 25s，一次性；替代的是每块 1–2 轮、每轮 2–4 万 tokens 的 LLM 重发。**总成本下降，召回上升。**

### 阶段 2：块级降级为「按需开页」（0.5 天）

块级只保留 `web_fetch`，且限制 1 轮；搜索入口全部走片源级 resolver。提示词同步改写：不再教模型「自己构造 query」，而是「引用【已核实术语】；仍存疑时只允许打开给定链接」。

## 七、不建议做的事

1. **换 Google**：本机 gtx 端点 429/421（项目已知坑）；**换百度**：实测桌面/移动 UA 全 403；**换 DDG**：12s 超时不可达。当前 cn.bing 已是国内最优解。
2. **引入 SerpAPI / 博查等付费搜索**：破坏工具箱「零第三方依赖、标准库出网」的定位，且需要用户配 key。
3. **把 wiki 全文塞进块级 prompt**：19,000 字符 × 每块 = 上下文爆炸；应只回填「官方名 + 一句依据」。
4. **让模型自由写 query**：实测已证明它会写出「作品 + 术语 + 官方名称」这种被 Bing 切词降级的长 query；必须模板化。

### 9.3 已修缺陷

1. 中文 URL 抓取 100% `UnicodeEncodeError` → `_encode_url` 分 path/query 编码，实测 `code=200 / 566,669 bytes`。

7. `think_rounds=0` 实际 32 轮硬顶且证据无预算 → 证据 8,000 / 音画 6,000 字符裁剪（保留最近片段）。

### 9.6 第三轮：库街区 / 森空岛免密接入（2026-11-18 用户实测反馈）

用户反馈「实测库街区 / 森空岛可以免密登录，继续调整」。复测后确认两站都有**无需账号的公开接口**，已接入。

**1. 库街区（已打通）**

- 真实请求：`POST https://api.kurobbs.com/wiki/core/catalogue/item/search`
  - `Content-Type: application/x-www-form-urlencoded;charset=UTF-8`（**不是 JSON**）
  - body：`keyword=<urlencoded>&page=1&limit=10`
  - headers：`wiki_type: 9`（鸣潮）/ `2`（战双）、`source: h5`、`devcode: <32 位随机串>`、`Referer: https://wiki.kurobbs.com/`、桌面 UA；**无 token**。
- 响应：`{"code":200,"data":{"results":{"records":[{"id":16790,"name":"卡提希娅",...}]}}}`；`code:500 系统异常` 即请求形态错（曾因 JSON body 触发）。
- 条目 URL：`https://wiki.kurobbs.com/{mc|pns}/item/{id}`（前端路由 `/:game/item/:id`）。
- 详情接口 `/wiki/core/entry/getEntryDetail` 等仍返回 `code:220 访问令牌不能为空`，因此只做「官方名 + 条目卡」证据。

**2. 森空岛（已打通）**

- `GET https://zonai.skland.com/web/v1/auth/refresh`（空 key 签名，仅需 timestamp）→ `{"code":0,"data":{"token":"2e07281c…"}}`。
- 签名公式（从 bundle 的 `encodeParams` + `getSign` 复刻，4 个真实样本 4/4 命中）：
  `sign = md5(hmac_sha256(path + query + timestamp + json({"platform":"3","timestamp":ts,"dId":did,"vName":"1.0.0"}), token))`
- `GET /web/v1/wiki/item/search?keyword=` → `data.items`（`itemId`/`name`/`mainType`/`subType`/`brief`）。
- `GET /web/v1/wiki/item/info?id=<itemId>` → `data.item.document.documentMap`，按 `blockIds` 递归（表格走 `cellMap.childIds`）可还原正文。
