# 校准能力「对象级」评估与优化方向

> 评估对象：`subtitle_calib_merged.py`（12,869 行，v2.3.0 工作树）
> 数据来源：2026-10-18 对本机脚本的实测统计（`data/tmp/_assess_object_level*.py`）
> 结论一句话：**知识层已经对象化了，执行层还是字符串级**——这是当前全部差距的总根源。

---

## 一、先把「对象级」拆成可验收的四层

「对象级校准」不是一个开关，而是四级能力。层与层之间是依赖关系，跳级做会返工。

| 层 | 能力 | 判定标准 | 当前状态 |
|---|---|---|---|
| **L1 知识层对象化** | 一个角色/地名/术语的全部知识（外文名、变体、条件、反例、出处）挂在同一个对象上 | 对象有唯一 id，可被 `lookup`/`export`/`lint` 整体操作 | 🟡 **半成**：有 `Entity` 类与 538 条注册，但只覆盖 21.9% 对象，且有 109 条重复身份 |
| **L2 执行层对象化** | 替换决策由「对象」做出：先确定这个 mention 指谁，再决定写什么 | `process()` 能拿到 canonical / 对象 id / 属性 | ❌ **空缺**：313 行主流程零引用，纯「错形 → 目标」字典替换 |
| **L3 mention 级对齐** | 参考行的实体出现位置与中文行的指称位置一一对上，同 cue 多对象不串 | 同一 cue 内多对象可按序次分别定名 | ❌ **空缺**：ctx 只是「参考行命中正则 → 整行全量替换该错形」 |
| **L4 文档级一致性** | 全片范围内同一对象只有一个译名，简称/全称/指代能归并 | 输出对象级一致性报告，不一致可自动收敛 | 🟡 **只有检测**：`audit` 扫 3 能报，但不能修、不能定名 |

横切层：**沉淀闭环**（人工修正 → 学习库 → 实体库）目前断在最后一步——`learned-promote --entities` 只打印桩代码，靠人工粘贴进 Python 源码。

所以更准确的描述是：**现在是一套「对象化的知识库」加一台「字符串级的执行器」，两层之间只有单向投影（`_register_entities`），没有反馈回路。**

## 二、现状量化（实测）

### 2.1 知识形态与规模

| 指标 | 数值 |
|---|---|
| 模式数 | 14（bi/ja/jpe/ko/wwoc/endo/endobi/endoko/ak/akko/zho/pgren/react/zel） |
| 无条件变体（错形→官方名） | 4,167 条 |
| 条件规则（ctx，参考行佐证） | 2,131 条 |
| 负向排除（exclude） | 51 条 |
| `ENTITIES` 注册条目 | 538 条 → **唯一 canonical 仅 429 个**（109 条重复，20.3%） |
| 其中「空壳对象」（无变体、无 ctx，对校准零贡献） | **150 条（27.9%）**，134 条是曲名 |
| 可执行实体 | 388 个 |
| `kb_view` 折叠出的对象总数 | **1,773 个** |
| **对象化率（可执行实体 / 对象总数）** | **21.9%** |

### 2.2 对象属性完整度（1773 个对象为分母）

| 属性 | 有值 | 覆盖率 |
|---|---|---|
| EN 官方名 | 292 | 16.5% |
| JA 官方名 | 52 | 2.9% |
| KO 官方名 | 34 | 1.9% |
| category | 426 | 24.0% |
| note（出处/戒律） | 429 | 24.2% |
| 三语全缺 | **1,439** | **81.1%** |

外文名不是装饰品——`audit` 的锚点就是从 `e.en/e.ja/e.ko` 生成的（bi 模式 545 个锚点）。81% 的对象没有外文名，等于**自动检测对它们完全失明**，只能靠手写 ctx 正则兜。

### 2.3 知识集中度（决定 MVP 边界）

| 覆盖对象数 | 累计变体 | 占知识量 |
|---|---|---|
| TOP 24 | 1,094 | 27.9% |
| TOP 75 | 1,876 | 47.9% |
| TOP 222 | 2,721 | 69.4% |
| **TOP 471（≥2 变体）** | **3,296** | **84.1%** |
| TOP 900 | 3,725 | 95.0% |

**结论：不需要把 1,773 个对象全部对象化。做完 TOP 471 就覆盖 84% 的知识量**，长尾 1,302 个「一次性键对」可以留在扁平表里长期共存。这条数据直接决定了优化方案的分期方式。

### 2.4 执行层实测（真实片源）

样本：`outbox/【字幕】WISH GRANTED!! Hsin 3.7 Main Story Quest FULL REACTION ｜ Wuthering Waves-校准终稿.srt`（2,341 cue，bi 模式，人工校过的「终稿」）

| 检查项 | 结果 |
|---|---|
| 全片重跑 `process()` 改动行 | **69 行**，全部是 ASR 断词归一（`Sim ul ac rum`、`Arb iter`、`She en`、`Sw ami`） |
| 耗时 | 0.38 s |
| `audit` 扫 1 拉丁残留 | 145 处（多为平台名/主播名，属正常） |
| `audit` 扫 2 错形残留（已佐证） | 4 处真漏校 |
| `audit` 扫 3 同词族一致性 | **85 处（3.6% cue）** |
| 典型残留 | `#156` Waking Moon Festival → 中文行写「觉醒之月节」，应为「朝月会」；`#211` 又写成「清醒节」；`#224` 写成「朝月大教堂」——**同一对象三种译法** |

注意 `process` 只改 69 行而 `audit` 报 85 处漏校：**执行器对「没登记过的错形」是零能力的**，它只能匹配已知字符串。这正是对象级要填的坑——对象级应该能判断「这个 cue 里有这个对象，但中文行没有它的任何合法译名」，进而生成候选，而不是等人工把第 N 种译法补进变体表。

## 三、五个结构性差距

### 差距 1｜执行层不认识对象（最根本）

`process()` 313 行里 `Entity`/`ENTITIES`/`canonical`/`category` 全部零引用（唯一命中在注释里）。替换路径是：

```
terms(dict: 错形 -> 官方名) → _compile_map(长键序) → 逐行 _replace_report → ctx 列表逐条全量替换
```

后果有三个，都能在数据里看到：

- **一个错形只能对应一个目标**。实测 bi 模式有 9 个错形被多条 ctx 指向不同官方名（19 个目标），ko 模式 7 个（14 个目标）。表里靠「规则顺序 + 长键在前」来消歧，本质是用顺序模拟优先级。
- **顺序依赖是隐性合同**。注释里写明「短键必须排在长键之后」，实测仍有 **38 处违例**（bi 13、ja 1、ko 24），例如「申」先于「申夫人」、「血灵」先于「血灵猎人」、「穆」先于「穆尤」。这类违例不会报错，只会静默产生「璇情贞」式残串。
- **替换是幂等的反面**。`鸣潮` 的 ctx 注释里明说「风化的波浪会被替换两次变成『鸣潮的鸣潮』」，所以只能靠「不收常用词」来躲，而不是靠对象身份约束。

### 差距 2｜对象身份不唯一

538 条注册里 47 个 canonical 重复登记：`心月狐×7`、`守岸人×6`、`鸣潮×6`、`残星会×5`、`漂泊者×4`、`锁暝×4`、`梦枢天罗×4`……

`_kb_view()` 用「later wins」把 note 用「；」拼接，看起来能合并，但**没有 id、没有合并语义、没有冲突检测**。追加式沉淀必然长成这样：每校准一部片就 append 一段，同一对象的「ASR 错形」「机翻义项」「组合词」分散在 7 个 `Entity(...)` 里，谁也不知道第 8 段会不会跟第 3 段打架。

### 差距 3｜对象属性残缺，元数据不参与决策

- 150 条空壳对象（27.9%）：登记了名字，但没有一条可执行知识。它们只让 `kb-export` 看起来更丰满。
- `modes` 在 `_kb_view` 里只从扁平表折叠填充，`ENTITIES` 循环不写 modes——纯元数据对象在对象视图里「不知道自己适用哪些片源」。
- `en/ja/ko` 只喂给 `audit`，**不参与 `process` 的锚点生成**。实测 213 个有 ctx 的实体共 598 条 ctx 规则，其中 **254 条（42.5%）正则里已经手写了自身外文名**（`\brover\b`、`\bSheen\b`、`Jinhsi|Ginshi`）——这近一半的锚点是纯机械劳动，本该由 `en=` 字段自动生成。另有 232 个实体有 EN 名但 ctx 为空。

### 差距 4｜没有 mention 级对齐，同 cue 多对象会串

真实样本里的两个硬证据：

- `#207` 参考行同时含 `Xuan` 和 `Yuan`，中文行是「原来这真的是玄元派的新训练」，`audit` 把两个锚点分别配到 `玄方/梦州` 和 `渊城/玄元境` 四个对象上——因为「玄元派」这个复合对象没登记，锚点只能乱配。
- `#235` 参考行的 `Sentinel` 一个锚点挂 4 个官方名（岁主 / 锁暝 / 岁主心月狐 / 军策府），当前逻辑是「任意一个出现在中文行就全部放过」，等于**放弃判断**。

对象级要做的正是这件事：`Sentinel` 先是类目词，落到具体角色时才是「心月狐」，落到职称时是「州监」——**这是对象消歧，不是字符串替换**。

### 差距 5｜检测强于修复，沉淀靠手工

- `audit` 三扫设计得相当好（扫 3 的「锚点命中但官方名缺失」是漏校主力来源，判断准确），但它只产出报告，不产出可执行的修复。
- 学习库 531 条候选（confirmed 345 / candidate 167 / rejected 19），`learned-promote --entities` 只能 `print()` 桩代码；固化路径是「打印 → 人工复制 → 粘贴进 12,869 行的 Python 源码 → 重跑 lint」。这是整个闭环里唯一的体力环节，也是对象库长期停在 21.9% 的直接原因。

## 四、优化方向（按 ROI 排序，四期）

### P0 · 对象身份治理（0.5～1 天，零行为风险）

目标：让「对象」这个概念在数据层立得住。

1. `Entity` 增加 `id`（稳定 slug，如 `ww.hsin`）与 `aliases`（官方简称/别译，**与 variants 错形严格分开**——现在 `NTE`、`COD`、`边狱巴士` 这类官方别名混在 variants 里，导致 audit 扫 3 把「已是官方简称」误报成漏校）。
2. 合并 109 条重复 canonical，重复登记列为 lint error。
3. `modes` 必填；曲名类（134 条）直接给 `modes=("wwoc", "endobi", ...)` 或标记 `kind="ost"` 不参与校准。
4. `kb-lint` 分级：`error`（重复 id / 空 modes / 变体冲突）阻断，`info`（缺 en）提示。

**验收**：`kb-lint` errors=0；`kb-export --json` 里每个对象有唯一 id。

### P1 · 对象索引 + 等价替换（3～5 天，影子模式）

目标：执行层第一次「看见」对象，但**输出与现状逐字节一致**。

1. 新增 `EntityIndex`：按 mode 构建 Aho-Corasick 自动机（canonical + variants + aliases + en/ja/ko），一次扫描得到 mention 列表 `(对象id, span, surface)`。替换掉现在「每行遍历 781 条 ctx 正则」的线性扫法（顺带把 0.38 s 再压一个量级）。
2. `resolve(cue)`：参考行 mention → 候选对象集；中文行 mention → 已用译名。两者交集即「本 cue 需要归一的对象」。
3. **影子双跑**：新旧引擎同时跑，diff 只允许出现在白名单（预期改进项）。不一致即回退，不切换。
4. ctx 的 38 处长键违例由 trie 最长匹配天然消除，不再依赖书写顺序。

**验收**：7 个 `outbox` 成品逐字节 diff 为空；`_negtest` 注入一条错误对象映射必须被抓到。

### P2 · mention 级消歧（1～2 周，核心价值）

目标：解决「一个锚点多个合法译名」和「同 cue 多对象串位」。

1. `Sentence` 级对齐：同一 cue 内按 mention 出现序次配对（参考行第 1 个对象 ↔ 中文行第 1 个指称），配不上时按邻近度，仍配不上则标 `unresolved` 交人工。
2. 对象属性进决策：`category`（角色/地名/类目词）+ `aliases` + `exclude` 共同决定 canonical。类目词（`Sentinel`→岁主）与具体对象（`Sentinel`→心月狐）靠 `category` 区分，而不是靠 ctx 顺序。
3. 复合对象支持：`玄元派` 这类「地名+势力」的组合，允许 `parent` 关系（`玄元派.parent = 玄方`），锚点先归父再归子。
4. 未登录对象自动成候选：参考行有 mention、中文行无任何合法译名 → 直接产出 `candidate`，进入学习库，不再只报告。

**验收**：样本片 `family_gap` 从 85 降到 ≤15；`#207`/`#235` 类多锚点 case 全部 `resolved`。

### P3 · 文档级定名与对象级报告（约 1 周）

目标：把「一次校准」升级为「一部片的对象台账」。

1. 两遍式：pass 1 收集全片每个对象的 mention 数、已用译名分布、首次出现位置；pass 2 按「多数 + 首次 + 官方名优先」定片内唯一译名并写回。
2. 新子命令 `calib-objects <srt>`：输出对象台账（对象 / 出现次数 / 译名变体 / 置信度 / 待决），CLI 与 GUI 共用。
3. 一致性门禁：同一对象出现 ≥3 次却 ≥2 种译名时退出码非 0，可挂进流水线。

**验收**：`#156/#211/#224`（朝月会）收敛为单一译名；台账可直接作为人工复核清单。

### P4 · 沉淀闭环自动化（约 3 天）

1. 实体库外置为 `data/entities/<game>.json`（按游戏分文件），Python 内嵌表保留为 fallback，`_register_entities` 改为「JSON 优先、内嵌兜底」。
2. `learned-promote` 直接写 JSON（带 id/mode/en 抽取），不再打印桩代码。
3. `audit` 扫 3 的 85 条残留自动生成 ctx 候选（锚点 + 中文行缺口 → 错形候选），人工只需「采纳/否决」二选一。

**验收**：新增一条 confirmed 规则 → 自动进实体库 → 下一部片立即生效，全程不改 Python 源码。

## 五、风险控制（沿用项目既有铁律）

| 风险 | 控制手段 |
|---|---|
| 执行层改造引入回归 | 影子双跑 + 7 个成品逐字节 diff；diff 非空白名单即阻断切换 |
| 只做正向校验（「看起来一样」） | 每一项都必须配负向测试：故意注入错误对象映射 / 故意删掉一条 ctx，确认 lint 或回归能抓到 |
| 一次性重写 `process` | 禁止。S1 只加索引做等价替换，行为不变；S2 起才逐分支切换，每切一处跑一次全量 diff |
| 知识库迁移丢数据 | JSON 导出与内嵌表双向 diff（对象数 / 变体数 / ctx 数三项计数必须相等），不等则拒绝启动 |
| 全量对象化成本失控 | 只做 TOP 471（84% 知识量），长尾 1,302 个留在扁平表，永不强行对象化 |

## 六、建议的最小起步

如果只做一件事：**P0 的身份治理 + P1 的对象索引（影子模式）**。

- 工作量小（约一周内可验证），不动替换决策，零回归风险；
- 立刻拿到两个可观测收益：`kb-lint` 从「6 问题 + 275 提示」变成可分级门禁；执行器有了对象视图，`audit` 的 545 个锚点从「手写正则抠字面量」升级为「对象自带外文名生成」；
- 为 P2 的 mention 消歧铺好数据结构——P2 才是真正拉开「字符串级 vs 对象级」差距的地方，但没有 P0/P1 的数据底座，P2 无从落地。

反过来，不建议的路线：直接给 `process` 加一堆 `if 对象 == ...` 的分支。那只是把 2,131 条 ctx 规则翻译成 2,131 个 if，维护成本更高，且仍然是字符串思维。
