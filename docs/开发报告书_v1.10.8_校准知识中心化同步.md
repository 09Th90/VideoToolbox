# 开发报告书：校准知识中心化同步改造（v1.10.8 提案）

- 提案日期：2026-09-12
- 前置版本：v1.10.7（`d7a5930`，多用户双向同步——启动拉取 + 条目级三方合并）
- 目标版本：v1.10.8
- 状态：待评审

---

## 一、背景与现状

v1.10.7 已实现「每个用户 = 一个对等节点」的同步架构：

```
启动：本地 ←拉取+条目级合并— GitHub main
退出：本地 —合并+推送→ GitHub main（pull-merge-then-push）
```

- 同步对象：`subtitle_calib_merged.py`（术语表 / CONTEXT_MAP 规则 / ENTITIES 实体）
  与 `subtitle_learned_kb.json`（learn 学习库候选）；
- 合并器：AST 条目级三方合并（本地 / 远程 / 基线快照），冲突保留本地并记日志，
  产物过「语法编译 + 实体注册冲突」两道门；
- 通道：GitHub Git Data API + curl，直连失败回退内置 mihomo 代理；
- 推送认证：每个用户本机的 `GH_TOKEN` / `gh auth` 凭据。

## 二、现架构的风险（本次改造的动因）

| # | 风险 | 说明 | 严重度 |
|---|------|------|--------|
| R1 | **坏内容自动扩散** | 两道门只能拦"跑不起来的脚本"，拦不住"能跑但语义错误"的条目（如错误术语映射）。任何客户端的错误沉淀会在下一轮拉取中自动传播给全部用户，无人工环节 | 高 |
| R2 | **写权限过度分散** | 每台用户机器都持有可写仓库的 token，而校准脚本是会被 import 执行的代码。任一客户端凭据泄露或被入侵，可向所有用户推送任意自动执行的代码 | 高 |
| R3 | **推送并发竞争** | 多人同时推送时后到者收到 422 失败，需等下个周期重试（安全但体验差、日志噪音） | 低 |

结论：方向上应收敛为「GitHub 为唯一权威源 + 单一合并发布者」，客户端退化为
只读消费方。该方案同时化解 R1（发布前有人工/CI 把关）、R2（写权限收敛到
CI 与维护者）、R3（单写者模型无竞争）。

## 三、目标架构

```
                    ┌─ 贡献通道（写） ──────────────┐
普通用户客户端        │                              │
  启动: 拉 main ────►│  contrib 分支（收件箱）        │
  （匿名读，无需token）│       │ push(带本人token)     │
  退出: 推 contrib ──►│       ▼                      │
                    │  GitHub Actions 工作流         │
                    │   1. kb-lint 校验              │
                    │   2. 条目级合并进 main          │
                    │   3. 失败→开 Issue 提请人工     │
                    │       ▼                       │
                    │  main 分支（已审核的发布版）     │◄── 分支保护：
                    └──────────────────────────────┘     仅 Actions 可写
```

要点：

1. **main = 唯一权威发布位**，受分支保护，只有 Actions（`GITHUB_TOKEN`）能推进；
2. **contrib = 收件箱**，客户端的退出推送目标从 main 改为 contrib，内容原样
   汇聚、互不覆盖（每人一次 commit，天然追加）；
3. **合并发布器跑在 GitHub Actions**（替代"本地常驻脚本"方案）：
   实时触发（push to contrib）+ 定时兜底（每日）；失败时开 Issue 提请维护者
   人工裁决，维护者本地什么都不用部署；
4. 普通用户的**启动拉取逻辑不变**（仍走条目级合并，防御本地未提交的修改被覆盖），
   但因 main 已是合并好的发布版，拉取通常退化为"检测一致，无事可做"。

### 与"本地部署脚本"方案的对比（评审用）

| 维度 | 本地脚本（提议原案） | GitHub Actions（本报告推荐） |
|------|--------------------|---------------------------|
| 实时性 | 依赖维护者开机 | push 即触发，真实时 |
| 可用性 | 单机、会停机 | GitHub 托管，免运维 |
| 凭据面 | 全权 token 落在本地 | 仅仓库内 `GITHUB_TOKEN` |
| 人工兜底 | 本地改完重跑 | Issue 通知 + 网页操作 |

## 四、开发任务分解

### 任务 1：抽出可复用合并核心（引擎重构，约 0.5 天）

- 新建 `src/calib_merge_core.py`，把 v1.10.7 的纯函数迁入：
  `merge_calib_script` / `merge_learned_kb` / `_registry_conflicts` /
  `_ast_module_tables` / `_dict_entries` / `_entity_fields` 等；
- `video_toolbox.py` 改为 `from calib_merge_core import ...`（保持向后兼容别名，
  自检断言不变）；
- 迁移后该模块零副作用（无目录创建、无环境变量改写），可在 CI 直接 import。

### 任务 2：CI 合并发布工作流（新建，约 1 天）

- 新建 `.github/workflows/calib-publish.yml`：
  - 触发：`push` 到 `contrib`（paths 限两个知识文件）+ `schedule`（每日兜底）
    + `workflow_dispatch`（手动）；
  - 步骤：checkout main+contrib → 运行 `tools/calib_ci_merge.py` →
    有变更则 commit 进 main 并推进 ref；校验失败则 `gh issue create` 通知；
- 新建 `tools/calib_ci_merge.py`（CI 侧入口，复用 `calib_merge_core`）：
  - 语义与客户端合并一致，但方向相反：**base = main 版本，
    incoming = contrib 上全部未合并提交的并集**；
  - 冲突条目不进 main：写 `conflicts-<日期>.json` 附件到自动开出的 Issue，
    等维护者裁决后手工并入；
  - 发布前跑脚本自带 `kb-lint` 与两道门（编译 + 注册冲突）；
- CI 里维护一个指针文件（如 `contrib/.merged_until` 记录已合并到的 commit），
  保证幂等，重跑不重复并入。

### 任务 3：客户端推送目标拆分（引擎改造，约 0.5 天）

- `video_toolbox.py`：
  - 新增常量 `SYNC_PUSH_BRANCH = "contrib"`（`SYNC_BRANCH` 保留为拉取分支
    = main，两个常量语义分开）；
  - `sync_calib_to_github()`：读 ref / 建 commit / PATCH ref 全部指向
    `SYNC_PUSH_BRANCH`；推送前不再调用 `_pull_and_merge`（防覆盖合并下沉到
    CI，contrib 上追加即可，无覆盖问题）；
  - `_pull_and_merge` / `sync_calib_on_startup()`：不变，仍拉 main；
  - 学习库推送策略改为"差异追加"：contrib 上以提交累积，不做远端合并
    （每次退出推一个新 commit，CI 负责归并）；
- 认证降级路径：无 token 时推送跳过（现状保持），启动拉取匿名可用（现状保持）。

### 任务 4：仓库与权限配置（人工操作 + 文档，约 0.5 天）

- GitHub 仓库设置：
  - `main` 分支保护：禁止直接 push（Maintainer 也走 PR 或 CI），
    Allow: 仅 `GITHUB_TOKEN`；
  - `contrib` 分支：允许协作者 push，允许 force-push 关闭（收件箱语义）；
  - Actions 权限：workflow 内 `contents: write`（main + contrib）；
- 确认现有用户的 token 权限可降级：后续新用户分发只需**无任何仓库权限**的
  安装包（拉取匿名），存量 token 建议到期后不再续期。

### 任务 5：自检与文档（约 0.5 天）

- `_selftest_gui.py` 新增断言：
  - `SYNC_PUSH_BRANCH == "contrib"` 且推送路径引用它（源码级断言，沿用现有风格）；
  - 推送前不再调用 `_pull_and_merge`（防覆盖逻辑归属 CI）；
  - `calib_merge_core` 可独立 import 且与引擎侧导出一致；
  - CI 入口脚本存在且包含 kb-lint 调用；
- `docs/使用说明.txt` 第九节改写为中心化同步说明（用户视角：
  "启动自动拿最新版 / 退出自动上交沉淀 / 坏内容到不了你机器"）；
- 版本号 1.10.7 → 1.10.8 全量更新（qt / iss / 安装器三件套）。

### 任务 6：灰度与回滚预案（约 0.5 天）

- 灰度顺序：先合入 CI 工作流并在仓库跑通（不动客户端）→ 客户端改推 contrib
  发一个测试版 → 观察一周 calib_sync.log 与 Actions 运行记录 → 全量；
- 回滚开关：客户端环境变量 `VT_CALIB_PUSH_BRANCH` 覆盖默认 contrib，
  异常时可指回 main 退回 v1.10.7 行为；CI 工作流可单独 disable 不影响客户端。

## 五、风险与对策（新架构残余风险）

| 风险 | 对策 |
|------|------|
| Actions 配额/故障导致知识停更 | 每日 schedule 兜底 + 客户端本地知识不受影响（只是暂时拿不到别人的新条目） |
| contrib 被塞垃圾提交 | CI 的 kb-lint + 两道门拦截；失败只进 Issue 不进 main；必要时收紧 contrib 写权限 |
| 合并冲突堆积无人裁决 | CI 自动开 Issue 带冲突清单，维护者按条目裁决（借鉴 learned-promote 的人工审阅流） |
| 客户端本地修改与 main 冲突 | 启动拉取仍是条目级三方合并（基线快照机制保留），冲突保留本地 |

## 六、验收标准

1. 两台机器模拟双用户：A 沉淀新术语 → A 退出推送 contrib → CI 合并发布 main
   → B 启动拉取后本地脚本含 A 的条目（全自动，无人工）；
2. 注入一条会触发注册冲突的恶意/错误沉淀：CI 拒绝合并、Issue 自动开出、
   main 内容不变、全体用户不受影响；
3. 普通客户端全程无 main 写权限（匿名读 + 仅 contrib 推送）验证通过；
4. 仓库自检 43+ 项（含新增断言）全部通过；真实脚本合并幂等性回归通过；
5. 断网/无 token 客户端：启动正常、本地校准功能完整可用（同步静默跳过）。
