# 下载报错 `EOF occurred in violation of protocol (_ssl.c:1007)` — 根因与修复

日期：2026-10-08

## 报错形态

```
Got error: EOF occurred in violation of protocol (_ssl.c:1007). Retrying
```

yt-dlp 会一直 Retrying 直到重试次数耗尽，最终失败。

## 根因

YouTube 的 `videoplayback` 直链在**签发时绑定了当时的出口 IP** —— URL 里带着 `ip=` 参数。

而本机的出网策略组会自动换节点：

| 策略组 | 类型 | 换节点的时机 |
|---|---|---|
| `AUTO` | url-test，interval 300s | 每 5 分钟重测，延迟差 >50ms 就切 |
| `SELECT` | **Fallback**，主节点为具体节点 | 主节点故障时切换 |

下载一个几十分钟的视频，中途只要换一次节点，**已签发的所有分片 URL 立刻全部失效**
（按 `ip=` 校验不通过），连接被对端掐断 —— 就是这个 EOF。

**关键点：换了 IP 之后，重试多少次都没用**，因为重试用的仍是那条绑定旧 IP 的 URL。

## 当场实测到的问题

`SELECT` 当时落在 **新加坡-IEPL-G1-2**，到 YouTube 延迟 **1844 ms**，是可用节点里最慢的一档。
慢 + 抖动 → 更容易触发 Fallback 切换。

实测各节点到 YouTube 的延迟（2026-10-08）：

| 节点 | 延迟 |
|---|---|
| 新加坡-智能-Netflix | **551 ms** ← 最快 |
| 新疆专用-台湾 | 718 ms |
| 韩国-IEPL-G1-1 | 1224 ms |
| 澳大利亚 | 1621 ms |
| 新加坡-IEPL-G1-2 | 1844 ms（当时在用） |
| 日本-IEPL-G1-1 / 美国-V1 | 超时不可用 |

## 已做的两件事

### 1. 立即改善（已执行，可逆）
把 `SELECT` 切到 `新加坡-智能-Netflix`（551ms）。随时可用 mihomo API 或客户端切回。

### 2. 产品级修复（已实现，默认开启）
下载期间**钉死出口节点**，结束后恢复 —— 不改用户的代理配置。

- 引擎侧 `src/video_toolbox.py`：
  `proxy_group_now()` / `proxy_node_delays()` / `pick_best_proxy_node()` /
  `proxy_lock_acquire()` / `proxy_lock_release()`
- 接入点：`src/video_toolbox_qt.py::DownloadPage._download_worker`
- 多任务并行用**引用计数**：首个任务才真正切换，末个任务结束时恢复原节点。
- 日志里会看到：`[代理] 已锁定出口节点 XXX（避免下载中途换 IP 导致分片失效）`

开关：

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `VT_PROXY_LOCK` | `1` | 设 `0` 关闭，退回「由 mihomo 自动切换」的旧行为 |
| `VT_MIHOMO_API` | `http://127.0.0.1:9098` | mihomo 的 external-controller |
| `VT_PROXY_GROUP` | `SELECT` | 出网策略组名 |

## 排查同类问题的顺序

1. 看 `SELECT` 当前落在哪个节点、延迟多少（别停在慢节点上还不自知）
2. 确认该节点稳定（连续几次 curl 都 200）
3. 仍报错 → 减少并行下载任务数（并发越高越容易触发限流与切换）
4. 再不行 → 让 NPE 第二引擎兜底（yt-dlp 各源全失败后自动接管）

## 附带修掉的三个 mihomo API 坑

1. `/proxies/<组>` 的 `all` 字段是**字符串数组**，不是对象数组
2. 切换节点的 PUT 返回 **204 空响应体**，无条件 `json.loads` 会抛异常
3. path 做 `quote` 时必须 `safe="/?=&:%~"` —— 否则 `delay?url=...` 的查询串被一起编码，路径失效
